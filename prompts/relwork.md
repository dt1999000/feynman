Write the related work and introduction for the LaTeX paper project and instructions in: $@

The first argument is the path to the user's LaTeX project, such as a venue template they have started filling in. Everything after it is optional focus or instructions (for example "related work only", "emphasize efficiency baselines", or "≤1 page"). If no path is given, use the current directory when it contains a `.tex` file with `\documentclass`; otherwise ask for the path.

## Workflow

1. **Read the project** — Find the root `.tex` file, follow `\input`/`\include`, and read the title, abstract, existing introduction, method, and results, plus any `README`, template instructions, and `% TODO` notes. Find the bibliography file and the citation package. Derive the slug from the paper's title, or from its topic when there is no title yet. Write `outputs/.plans/<slug>.md` with: the project path and root file; a 3–5 sentence summary of what the paper does; its stated contributions; the closest work it already cites (keys from the existing `.bib`); 3–6 related-work themes to search; the target files for each section; length limits; and a task ledger and verification log. If the project has no abstract or method text yet, say in the plan that the introduction will carry `% TODO(feynman)` placeholders for the contributions, and still write the related work. Summarize the plan to the user in a few lines and continue immediately; do not wait for confirmation unless the user asked to review the plan.
2. **Gather** — Spawn one `researcher` per theme in parallel, each with `output` set to `outputs/.drafts/<slug>-research-<theme>.md`. Tell each researcher to: start from the paper summary and the papers the project already cites; expand one hop through the citation graph of the closest papers (`openalex_references` and `openalex_citations`); and record for every paper its title, year, first author, DOI or arXiv ID, a one-line summary of its method, and one line on how it relates to the user's paper (`builds-on`, `competes-with`, or `background`). Papers without a DOI or arXiv ID cannot be cited and must say so.
3. **Select** — Read the research files and choose the papers the sections will cite, usually 20–50 for a conference paper: every `competes-with` paper the user's evaluation or claims depend on, the seminal `builds-on` work, and enough `background` for the introduction's framing. Record the selection and the reason for each paper in the plan.
4. **Bibliography** — Call `feynman_bibtex` with the selected DOIs and arXiv IDs and the project's `.bib` path as `output` (or `<project>/refs.bib` when the project has none). It skips papers already in the file and returns the keys to cite. Compare each returned title, year, and first author with the selection. Look up failed identifiers again with `feynman_science_database_search`; drop papers that still fail and note them in the plan.
5. **Write** — Spawn the `latex-writer` with: the project path; the target sections (related work, introduction, or both, as the user asked); the plan path; the research file paths; the `.bib` path and the keys it may cite; and the user's instructions. Write the related work first, then the introduction, so the introduction's gap statement matches the related work.
6. **Check citations** — Spawn the `verifier` on the written `.tex` files with these instructions in the task: this is a LaTeX artifact, so keep `\cite` keys and do not convert them to `[n]` or add a Sources section; check that every cited key exists in the `.bib`; check against the research files and the paper's record that each citation supports its sentence; replace an unsupported citation with a supported key or a `% TODO(feynman)` note; and write its findings to `outputs/<slug>-verification.md`.
7. **Review** — Spawn the `reviewer` on the sections with the plan as context. Ask it to check for missing closest work or baselines, an unfair or vague description of competing work, contributions stated more strongly than the project's results support, and an introduction gap that does not match the related work. Fix FATAL issues with the `latex-writer` and run one more citation check if citations changed.
8. **Deliver** — If a LaTeX engine is installed, compile the root file into a scratch directory (`latexmk -pdf -outdir=.feynman-build` or `tectonic`) and report the result; otherwise say it was not compiled. Write `outputs/<slug>.provenance.md` with: the date, the project path, papers found vs. selected vs. cited, identifiers that failed to resolve, the verification and review status, the compile status, and the intermediate files used. Tell the user which files changed, the `\input` lines or preamble changes they still need to make, and every `% TODO(feynman)` left in the text. Before you stop, verify on disk that the section files, the `.bib`, and the provenance file exist.
